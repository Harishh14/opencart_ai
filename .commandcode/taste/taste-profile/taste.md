# Taste profile
- Prefers a minimal-touch approach during scaffolding: preserve all existing files and configuration, create only what is missing, and never overwrite or delete existing implementation files unnecessarily. Confidence: 0.85
- When a requested change touches files that already exist (e.g., converting file types or updating content), prefers updating those existing files in place over creating new files — explicitly dislikes having new files created when the existing ones could just be modified. Confidence: 0.8
- When a structural change could require touching existing config (e.g., updating a Playwright `testDir` to match a new nested layout), prefers to leave config untouched rather than modify working files, even if it means the new folders aren't auto-discovered yet. Confidence: 0.8
- When an existing config references a missing file or a requested layout conflicts with current config behavior, prefers that the agent ask a clarifying question before changing anything rather than guessing. Confidence: 0.7
- Dislikes `.gitkeep` placeholder files used to keep empty directories versionable; when scaffolding, do not drop placeholder marker files into folders unless asked. Confidence: 0.8
- Organizes Playwright + TypeScript automation projects in a layered structure: separate test suites by type (`tests/web`, `tests/api`, `tests/db`) with dedicated support folders for `pages`, `fixtures`, `testdata`, `api/endpoints`, `api/schemas`, `utils`, `prompts`, `custom-report`, and `reports`, plus `.env` at root. Confidence: 0.7
- Prefers API endpoint URLs to be centralized in a dedicated routes module (e.g., `api/endpoints/routes.ts`) exposing per-resource constants, parameterized route builders, and a base-URL helper, so tests never hard-code endpoint URL strings inline. Confidence: 0.9
- After creating or altering a directory structure, expects a final directory tree and an explicit list of newly created files (vs. existing files preserved) so the change footprint is clear. Confidence: 0.8
- Prefers test data to be supplied in multiple formats (JSON, CSV, and XLSX) for the same dataset, stored in the `testdata` folder, so the data can be consumed by data-driven tests regardless of the loader. Confidence: 0.7
- Prefers test data files to bundle one valid record together with additional invalid records (e.g., wrong password, unknown username) so the same dataset supports both positive and negative test scenarios. Confidence: 0.7
- Wants all endpoint routes defined in a single routes module, grouped by resource with banner comments separating each section, parallel meaningful route keys across resources (e.g., getAll, getById, getByLimit, create, update, delete), and plain objects exposing method/path/query params/sample body so Playwright API tests can import and reuse them. Confidence: 0.8
- Prefers response-validation schemas written in JSON Schema format and stored as standalone `.json` files (one per resource, reusable with AJV), not as JS/TS modules exporting schema objects; expects per-field type constraints plus format checks (e.g., email, URI) that match the documented response contract. Confidence: 0.95
- In a TypeScript/Playwright project, code artifacts should be authored as TypeScript (`.ts`, e.g., `routes.ts`), not plain JavaScript (`.js`), to match the project's existing module conventions. Confidence: 0.9
- Keeps scaffolding scope tight: create only the files explicitly requested — no test cases and no extra request-wrapper/helper functions unless the user asks for them. Confidence: 0.7
- When delivering scaffolding code, wants the response to clearly explain where each new file should be placed in the project (exact path per file), in addition to the code itself. Confidence: 0.6
- Prefers reusing existing utilities, helpers, and installed dependencies over creating new code: explicitly asks to reuse what exists rather than duplicate functionality, avoid creating unnecessary utilities, and update an existing file only when necessary. Confidence: 0.85
